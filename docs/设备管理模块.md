# 设备管理模块说明

新增设备管理业务模块（后端 `jeecg-module-device` + 前端 `views/device/device`），核心是**设备状态的流转限制与操作留痕**。

## 1. 状态定义

数据字典：`device_status`（脚本已内置，可在“系统管理 → 数据字典”中维护）

| 值 | 状态 | 说明 |
| --- | --- | --- |
| `1` | 在用 | 新建设备的默认状态 |
| `2` | 维修 | 只能恢复为“在用” |
| `3` | 停用 | 可重新启用、转维修或报废 |
| `4` | 报废 | **终态**，不能再变更（不能回到在用） |

## 2. 流转规则

流转矩阵由后端枚举 `org.jeecg.modules.device.enums.DeviceStatusEnum` 统一实现，前端 `device.data.ts` 中维护同构矩阵用于按钮展示，**最终以后端校验为准**：

| 当前状态 | 允许的目标状态 |
| --- | --- |
| 在用 | 维修、停用、报废 |
| 维修 | **仅在用（恢复，必须填写恢复说明）** |
| 停用 | 在用、维修、报废 |
| 报废 | 无（终态，前端按钮置灰，后端接口同样拒绝） |

额外限制：

- 新建设备无论传什么状态，后端一律落为“在用”，并写入一条 `CREATE` 初始记录。
- 普通“编辑”接口不允许修改 `status`，一旦传入的状态与库内不一致直接报错，状态只能走专用接口 `POST /device/device/changeStatus`，避免绕过流转限制。
- 维修 → 在用（设备恢复）时 `remark` 必填，纯空格也会被拒绝。
- 状态更新与记录写入在同一事务（`@Transactional`），失败整体回滚。

## 3. 操作记录（追溯）

每次状态变化都会写入 `device_status_record` 表：设备ID、变更前/后状态、操作类型（`CREATE` 新建 / `CHANGE` 流转）、变更说明、操作时间、操作人（由框架拦截器自动填充）。

列表页“更多 → 操作记录”可查看单台设备的全部状态历史，按操作时间倒序。
同时状态变更接口带有 `@AutoLog("设备-状态变更")`，也会进入系统操作日志。

## 4. 接口一览（`/device`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/device/device/list` | 设备分页查询 |
| POST | `/device/device/add` | 新增设备（默认在用，写初始记录） |
| POST/PUT | `/device/device/edit` | 编辑设备基础信息（禁止改状态） |
| POST | `/device/device/changeStatus` | 状态流转（校验 + 必填说明 + 写记录） |
| GET | `/device/device/queryById` | 设备详情 |
| DELETE | `/device/device/delete`、`/deleteBatch` | 删除/批量删除 |
| GET | `/device/statusRecord/list?deviceId=` | 状态操作记录分页查询 |
| GET/POST | `/device/device/exportXls`、`/importExcel` | 导入导出 |

## 5. 数据库初始化

- MySQL：`backend/db/device/device-mysql.sql`
- SQL Server：`backend/db/device/device-sqlserver.sql`（项目默认库为 SQL Server，在 `db-init` 完成基础库初始化后，于业务库中手工执行一次）

脚本内容：业务表 2 张（`device_info`、`device_status_record`）、字典 `device_status`/`device_type` 及字典项、“设备管理”菜单及 5 个按钮权限。admin 超管登录后自动拥有全部权限；其他角色需在“角色管理”中勾选授权。

## 6. 单元测试

`DeviceStatusEnumTest` 覆盖流转矩阵（在用/维修/停用/报废）与非法状态入参，可执行：

```bash
mvn -pl jeecg-boot-module/jeecg-module-device test
```
